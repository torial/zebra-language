# Moving the toolchain from Zig 0.16 to 0.17

**Status:** Phase A (one source tree that builds and behaves under both 0.16 and 0.17) in
progress, 2026-10-03. Phases B (switch the toolchain) and C (drop the 0.16 spellings) not
started. Decided by Sean, 2026-10-03: migrate ("not much effort and then we get the latest
Zig"); the repo pins 0.17 through `ZEBRA_ZIG` while the machine default stays 0.16 until the
other projects on it are verified; zigzag / the TUI backend is dropped (refused by name, the
section file kept); zig-libui-ng is ported and pushed.

## Why a dual-version phase

The compiler regenerates itself with the PREVIOUS build (N-1). A commit whose emitted Zig
only 0.17 accepts could not be regenerated by a compiler built with 0.16, and vice versa.
So the switch needs one commit that both toolchains build — the same isolation tactic as
BUG-501's prep (`docs/design/container_reference_semantics.md` §9): spell every
version-sensitive construct through a form valid in both, prove it under both, then switch.

## What 0.17 changes that Zebra touches (measured, not read)

Measured against the 0.17.0 release on 2026-10-03 (`~/.zvm/0.17.0`). The release notes were
wrong twice for us: `std.heap.StackFallbackAllocator` is not "reworked" but REMOVED (its
replacement is `BufferFirstAllocator`), and `std.zig.Subsystem.Windows` was removed without a
note (0.16 had it as a deprecated alias of `.windows`).

| change | where in Zebra | dual-version spelling |
|---|---|---|
| array multiplication `x ** n` removed | runtime (6), libui section (8 incl. `.{null} ** n`), coverage emit | `@splat` with the result type |
| `@typeInfo` struct-of-arrays (`param_types`, `field_names`/`field_types`) | runtime closure/MVU plumbing, deep copy, `_zbr_show` | `_zbr_fn_info_param`, `_zbr_fn_info_arity`, `_zbr_field_names`, `_zbr_field_types` (comptime `@hasField` on the info type; the untaken branch is never analysed) |
| `Allocator.dupeZ` removed | runtime, libui section, DynLib emit | `dupeSentinel(u8, x, 0)` (present in 0.16) |
| `std.ascii.indexOfIgnoreCase` removed | runtime HTTP | `findIgnoreCase` (present in 0.16) |
| `errdefer \|e\|` capture removed (a PARSE error, so no comptime switch can hide it) | the throwing `main` (BUG-466) | the body moves to `_zbr_main_body`; `main` keeps the prologue and its defers and does `return _zbr_main_body() catch \|e\| _zbr_uncaught(e)` — still before the arena defer runs |
| `@cImport` removed | `use foo` with `foo.h`; `--target node-addon` | the driver runs `zig translate-c` (both versions have it; `-lc -I -D` behave the same) and writes `_zbr_c_<alias>.zig` / `_zbr_c_napi.zig` beside the emitted file (`cHeaderZigFile`, one function for both sides) |
| `std.heap.stackFallback` removed | `allocate StackFallback(n)()` | runtime `_ZbrStackFallback(n)` picks `BufferFirstAllocator` or `stackFallback` |
| `@hasDecl` sees only `pub` decls, even in the same file (SILENT) | closure `call` was non-`pub` in the inline runtime shape | always `pub fn call` (`rtPub` removed) |
| Build API: `b.args` / `b.build_root` removed; Optimize tags renamed | `build.zig`, the libui and tui scaffolds | `addPassthruArgs` behind `@hasDecl`; `isDebug()` by tag name; `buildRootDir()` behind `@hasField` |
| `builtin.os` / `.cpu` deprecated (removed in 0.18) | runtime, `zig"…"` literals in main.zbr | `builtin.target.os` (valid in both) |
| `std.os.linux.waitpid(pid, status: *u32 -> *i32, ...)` (unmentioned; found by the first LINUX CI build, BUG-523 -- no Windows build analyses it) | `sys.spawn`'s `isRunning`, Linux without libc | the status type is taken from `waitpid`'s own signature and `@bitCast`. Gate: `cross-sema` analyses windows / linux / linux-gnu |

Found by the FULL smoke suite run under 0.17 (`ZEBRA_ZIG` + PATH at 0.17), after the
60-program sample had passed:

| change | where | dual-version spelling |
|---|---|---|
| `std.hash.crc.Crc32` removed (crc namespace audit) | runtime `hashCrc32` | `std.hash.Crc32` (present in 0.16) |
| ArrayList gained a `pointer_stability` field, so a field-by-field literal `.{ .items = &.{}, .capacity = 0 }` no longer compiles | runtime regex engine (5 sites) | `.empty` |
| **the self-hosted COFF linker writes an import library beside every image and fails on ANY absolute output path** (`flushing implib '...\x.lib' failed: BadPathName`, exit 1 with the exe already written) -- a 0.17 bug, not ours | the driver's fast path (`-fno-llvm -fno-lld`) | `-fno-emit-implib` (accepted by 0.16; an exe needs no implib) |

The linker bug made EVERY fast build fail and fall back to the ~6x slower LLVM path without a
word, and that fallback exposed BUG-522 (the LLVM run path never handed the program
`ZEBRA_COMPILER`), a pre-existing bug that also affected 0.16 programs with an `extern`, a C
dependency or sqlite. A first hypothesis -- that 0.17 no longer inherits a variable set after
startup -- was tested and failed (a 0.17-built parent passes it exactly as 0.16 does).

Audited and NOT affected: `@bitCast` (every use is integer-to-integer; the silent change is for
arrays, vectors and extern structs), `std.mem.eql` on floats (every use compares bytes), the
`-OReleaseFast` CLI spelling (both versions accept it).

The linker bug was NOT reported upstream: the Zig team does not accept LLM-created content
(Sean, 2026-10-03). The workaround stays until Phase C re-tests it.

## Phase B (2026-10-03/04): the toolchain is 0.17

- **The pin.** `.zig-version` (0.17.0) and `tools/zig_toolchain.sh`, which every tool sources:
  it puts that exact zig first on PATH, exports `ZEBRA_ZIG` (the compiler's `zigExe()`
  honours it), and REFUSES on a version mismatch. It replaced 18 shell scripts' and 2 Python
  tools' `~/.zvm/bin` -- the machine's SHARED default, which stays 0.16 for the other projects
  (Sean's call) and would have kept every tool on 0.16 silently.
- **History.** `regen_recover --from <sha>` builds a commit with THAT commit's
  `.zig-version` (none = 0.16.0). The N-1 anchor moved to `n1-anchor-2026-10-03` = f5afd86
  (Phase A.2, the first commit that builds under both); rc4's anchor is 0.16-only.
- **CI and release** download 0.17.0 (checksums from ziglang.org's index, mapped one for one);
  release tags are `_zig0.17`.
- **tui is refused by name** (zigzag has no 0.17 support); the section file stays. Its
  coverage moved: `gui_scaffold_check` reads the libui_ng scaffold (`--scaffold-only`) for
  BUG-229's shape and runs the program on the STUB backend for 100 counted frames
  (`ZEBRA_GUI_STUB_FRAMES`, new) for BUG-358's; the BUG-229 smoke leg is a PIN that fails the
  day tui returns. Lost, and said so: a real backend's own startup is run by nothing.
- **A probe 0.17 broke without breaking the code.** release-mode's BUG-468 stack-overflow
  probe allocated a list per frame; under 0.17 the heap ran out first (`panic: OOM`). The
  handler was fine -- a non-allocating probe prints "Stack overflow" on both toolchains in
  both runtime shapes.
- Measured: the DAILY tier under 0.17 passed everything but four gates, all fixed above
  (two doc counts, the glfw-refusal wording, BUG-229's tui leg, the stack probe):
  output_sweep 466 identical, full_sweep / divergence 0 regressions, libui-pin-build (a
  stranger's build from the pin) PASS.
