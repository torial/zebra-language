# The 1.0 stability promise — what is frozen, what is not, and how things leave

**Status:** DRAFT for Sean's red pen (Fable 5.1, 2026-09-14). Nothing here is in force
until it is adopted; the instrument half (`docs/SURFACE.md`, gate `surface-freeze`) is
already live and is what this policy would be a policy *about*.
**Context:** NEXT_STEPS_to_1.0 §15 says 1.0 "locks the API surface with a stability
promise" and, until 2026-09-14, no document said what the surface was or what "locked"
committed anyone to. PRINCIPLES.md already fixes the mechanism for removals ("a
compatibility transform is a mechanical rewriter, never a permanent acceptor"); this page
states the promise that mechanism serves.

## 1. The promise, in one paragraph

A program that compiles and runs correctly on Zebra 1.x compiles and runs correctly, with
the same output, on every later 1.y — or the compiler tells you, at compile time, with a
diagnostic naming the release that will break it and the rewrite that fixes it, at least
one minor release before it does. "Correctly" means the behaviour QUICKSTART documents;
behaviour a program relied on by accident (see §3) is not covered.

## 2. What is frozen — the surface

The set is **derived, not described**: `docs/SURFACE.md`, regenerated by
`tools/surface_inventory.py --write` and gated by `surface-freeze`. As of 2026-09-14 that
is the 79 keywords, the command forms and flags in `zebra --help`, the 31 stdlib namespaces
with their 171 static members, the 7 generic constructors, and the builtin receiver methods
of `str`, `List`, `HashMap`, `Set` and `JsonValue`. A change to any line of that file
after 1.0 is a promise change and needs, in the same commit, a `CHANGELOG.md` line and —
for a removal — the deprecation steps in §4.

**Not yet in the derived set, and therefore covered only by QUICKSTART's word until the
tool learns to see them:** instance methods on the runtime object types that have no
`Type_` variant of their own (`DateTime`, `File` handles, `HttpResponse`, the GUI widget
structs), argument arities and types. The sixteen types that do have a variant (`Regex`,
`Timer`, `StringBuilder`, `SysProcess`, `Build`/`BuildTarget`, the `Ws`/`Tcp`/`Udp`
connections, `Sqlite*`, `CodeEditor`, `Gui`, `HttpRequest`, `Chan(T)`) were closed on
2026-09-15 and are in the derived set. Closing the rest is a pre-1.0 task on the tool,
not a reason to promise less.

## 3. What is NOT frozen — say it, so absence reads as a decision

- The **text** of diagnostics (their *presence* and their *position* are frozen: a
  program the front end refuses in 1.0 is refused in 1.y, and `diag-columns` keeps the
  coordinate).
- The **shape of the emitted Zig** and anything reachable only through `zig"..."`
  literals or `--emit-zig`. A `zig"..."` literal is a contract with Zig, not with Zebra.
- **`Math` beyond its listed members.** The derivation found `Math` OPEN: an unlisted
  name passes through to `std.math.<name>` and is judged by Zig. The listed 33 are
  promised; `Math.sin` works today by pass-through and is promised only once listed.
- Anything marked **experimental** in `--help`, QUICKSTART, or the release notes
  (`--target node-addon`'s Node-version range; macOS left this list on 2026-09-15).
- **Performance.** Same output, not same speed; `--release`/`--turbo` remain independent
  and composable but their effect sizes are not a contract.
- **Zig-version portability.** A release is pinned to the Zig it bundles. A program that
  builds with the bundled Zig is the promise; "builds with whatever Zig is on PATH" is
  not, and `ZEBRA_ZIG` exists precisely so that a user who overrides the pin knows they
  have.
- Anything in `zig-out/bin` other than `zebra` itself (the preamble and GUI section files
  it reads, `vendor/sqlite`). The bootstrap compiler, which this line used to name, was
  retired 2026-09-16.

## 4. How something leaves — deprecation by migration

Zebra has no warning tier today (everything is an error or silence), and a surface that
can never warn can only ever break. So the **warning tier is a prerequisite of 1.0**, not
an item beside it. With it, a removal takes three steps across at least two minor
releases:

1. **Announce** (release N): the construct still works; the compiler emits a warning
   naming the release it stops in and the rewrite. `--warnings-as-errors` turns it red
   for those who want the tighter contract. The `CHANGELOG.md` line and the
   `docs/SURFACE.md` diff land together.
2. **Provide the rewriter** (release N, same commit): a Transform that rewrites N-syntax
   to N+1-syntax — PRINCIPLES.md's "mechanical rewriter, never a permanent acceptor".
   `zebra fmt --migrate` is the natural home. A removal without a rewriter does not ship.
3. **Remove** (release N+1 or later): the construct is refused with the same diagnostic
   the warning carried, now as an error, still naming the rewriter.

Additions need only step 0: a `SURFACE.md` diff and a `CHANGELOG.md` line. An addition
cannot break a 1.x program — except by taking a keyword, which is why new keywords are
the one addition that follows the removal schedule (they remove a name from the user's
namespace: `lint_reserved_words` is the receipt for what an idle keyword costs).

## 5. Versions

`MAJOR.MINOR.PATCH` (`_zbr_version` in `selfhost/stdlib_preamble.zig`, tag
`vX.Y.Z_zig0.16`). PATCH: fixes only, no `SURFACE.md` diff. MINOR: additions, announced
removals, the warning-then-remove schedule above. MAJOR: the promise resets, and 1.x
programs are carried by the migration transforms rather than by acceptance. A project may
state the version it was tested against (`zebra = "^1.0"` in its build file — the pin
proposed in NEXT_STEPS_to_1.0 item 3); the compiler refuses with a clear line when it
does not satisfy it.

## 6. What 1.0 does not include (non-goals, so the omissions are decisions)

- No package manager. `use` resolves paths; third-party code is a checkout or a
  `BuildTarget.linkLib`. A package story is 1.x work and will not change `use`.
- No editor support beyond the LSP and zebra-ide. A TextMate/tree-sitter grammar is a
  small adoption item and welcome, but not promised.
- No portability across Zig versions (§3), no evented I/O runtime (servers are
  thread-per-connection; C10k is post-1.0, see §28j's xsync note), no runtime CPU
  dispatch for SIMD.
- No `defer`/`errdefer`: freed as identifiers on 2026-09-15 (Sean). `using` is the
  resource-scope construct; a Zig-shaped `defer` was bleed-through.

## 7. What adopting this would change tomorrow

Nothing in the compiler. Three things in practice: the warning tier moves ahead of the
freeze in the queue; every `SURFACE.md` diff gets a CHANGELOG line (a `doc-lint` rule can
enforce that the two files change together); and `Math`'s OPEN status gets a decision —
list the members that are promised, or close the pass-through.
